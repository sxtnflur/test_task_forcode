# Gate nambaone

Платежный гейт для [NambaOne Merchant Web API](https://merchant-api-docs.rps.kg/).
Реализует протокол гейта v2 процессинга (`gate_lib`) поверх одноразовых платежных ссылок NambaOne.

Поток платежа:

1. `sale` без `card_token` создает одноразовую платежную ссылку (`externalId = invoice_id`)
   и возвращает редирект на нее (или на страницу secure redirect, если она настроена у терминала).
2. Плательщик оплачивает ссылку в приложении Namba One.
3. NambaOne присылает вебхук на `/callback/invoice`.
4. Гейт запрашивает актуальный статус через API и отмечает счет в процессинге оплаченным или неуспешным.

Что поддерживается: `sale` (без карты), `status`, `refund`, `refund_status`, `balance`, вебхуки о платежах.
Что не поддерживается и отвечает `not_supported`: `sale` с картой, `p2p_selector_sale`, `withdrawal`,
`withdrawal_status`, `sale_confirm` — NambaOne принимает платежи только в своем приложении.


## Запуск

Переменные окружения (`.env`):

| Переменная | Назначение |
|---|---|
| `CDS_URL`, `CDS_AUTH_TOKEN` | Card Data Storage |
| `SBANK_API_BASE_URL`, `SBANK_RADMIN_BASE_URL`, `SBANK_API_AUTH_TOKEN` | API процессинга |
| `SECURE_REDIRECT_KEY` | ключ подписи secure redirect; без него sale для терминалов с `secure_redirect_url` отклоняется |
| `NOTIFICATIONS_PREFIX` | префикс эндпоинтов вебхуков: `{prefix}/callback/invoice` |

```bash
docker compose up web
```

Тесты:

```bash
pytest src libs
```


## Изменения шаблона

`api/schemas.py -> gate_nambaone/schemas/terminal_data.py, gate_nambaone/schemas/notifications.py`

Перенес для того, чтобы gate_nambaone не знал об api,
чтобы можно было подключить и другие контроллеры в будущем.
Можно было бы вместо этого сделать отдельно DTO, но это уже излишнее дублирование схем.

В `api/` добавились `server.py`, `errors.py`, `routers/`

`errors.py`
Нужно зарегистрировать и известные, и неизвестные 5хх ошибки.
Неизвестная ошибка отдает 500 без поля `status`: итог операции неизвестен, и процессинг
не должен считать ее неуспешной. `NotificationRetryableError` превращается в 503,
чтобы NambaOne повторил вебхук.

`server.py`
Для удобства сборки FastAPI():
здесь регистрация роутеров, ошибок, middlewares в раздельных методах.

`routers/`
Спрятал все роутеры в отдельный пакет.

Добавил `client/`
Для реализации принципа единой ответственности. Чтобы сервис не знал, используем мы httpx или aiohttp или др.
Реализация на httpx — `HttpxAPIClient`; единственное место, которое знает, что к NambaOne ходим через httpx, — `api/deps.py`.

`libs/` — локальные реализации внутренних библиотек (`gate_lib`, `utils`, `cds_client`, `sbank_client`)
с теми же путями импорта. Подробнее в [libs/README.md](libs/README.md).

`aiojobs` - больше не используется, так как он был в шаблоне для выплат, а в NambaOneClient нет выплат.


## Структура

```
src/
  api/                       # FastAPI: роутеры, зависимости, обработчики ошибок
  client/                    # HTTP-транспорт (не знает про NambaOne)
  gate_nambaone/
    nambaone/                # клиент API NambaOne: знает только протокол провайдера
      sender.py              # подпись, отправка запроса, разбор конверта ответа
      api/                   # методы по ресурсам: payments, refunds, merchant
      client.py              # NambaOneClient (фасад) и NambaOneConnector
      schemas/, errors.py, error_codes.py, amounts.py
    operations/              # сценарии гейта из нескольких шагов (sale, refund, поиск заказа)
    gate_nambaone.py         # адаптер протокола процессинга
    secure_redirect.py       # secure redirect, не зависит от провайдера
    validators.py            # проверка валюты и суммы до обращения к NambaOne
    errors.py                # ошибки операций гейта
    schemas/                 # настройки терминала и вебхуки
  status_mapper.py           # статусы NambaOne -> статусы протокола
  log_masking.py             # поля, скрываемые в логах
```


## gate_nambaone/nambaone/

Клиент разделен на слои, каждый со своей ответственностью:

- `NambaOneRequestSender` — вся логика отправки запроса: подпись, перехватывание исключений, валидация ответа.
  Ничего не знает о конкретных методах.
- `PaymentsApi`, `RefundsApi`, `MerchantApi` — знают только об эндпоинтах NambaOne.
- `NambaOneClient` — фасад над ними для одного аккаунта мерчанта (`nambaone.payments.get_one_time_order(...)`).
  Собирается в `NambaOneConnector.connect()` на каждый терминал: у каждого терминала свои секрет и прокси.

Пакет не зависит от `gate_lib`, процессинга и настроек гейта. Тогда как `GateNambaOne` знает еще и о sbank,
и о нашем формате ответа, и пр. Сценарии, где нужны и NambaOne, и процессинг, лежат в `operations/`.


## Принятые решения

### Ошибки и статусы

Каждая ошибка операции — либо `OperationRejected` (операция точно не состоялась, деньги не двигались),
либо `OperationUncertain` (итог неизвестен, деньги могли двинуться). Какой статус протокола это значит,
решает конкретная операция:

| Операция | Отказ | Неизвестный итог |
|---|---|---|
| `sale` | `failed` | `failed` — ссылка не отдана плательщику, оплаты быть не может |
| `refund` | `failed` | `pending` — возврат мог создаться |
| `status`, `refund_status` | `pending` | `pending` |

Отказ NambaOne (`"status": "ERROR"`) — это `OperationRejected`, кроме `UNKNOWN_ERROR`.
Таймаут, ошибка соединения, непонятный ответ — `OperationUncertain` с кодом `provider_unavailable`.

Валюта (только KGS) и сумма (только целые тыйыны) проверяются до обращения к NambaOne и дают `validation_error`.

### Статусы NambaOne

Сопоставление в `status_mapper.py`. `REFUNDED` у платежа — это `complete`: сам платеж прошел,
возвраты отслеживаются отдельно. Неизвестный статус — `pending`, чтобы новый статус NambaOne
не ломал разбор и не закрывал платеж по ошибке.

Заказ по одноразовой ссылке существует с момента ее создания: неоплаченная ссылка — это статус `CREATED`.
Поэтому пустой ответ (`"status": "OK"` без данных) значит, что NambaOne не знает ссылку.
`NambaOneInvalidResponseError` несет флаг `is_empty`, а что он значит, решает вызывающий код для конкретного метода:
для поиска заказа это `PaymentOrderNotFound`, для остальных методов — сбой.

### Вебхуки

Вебхуки NambaOne не подписаны, поэтому их содержимому не доверяю: из вебхука берется только `externalId`
(= `invoice_id`), счет и терминал берутся из процессинга, а статус запрашивается через API.

- Статус еще не финальный или процессинг недоступен — ответ 503, NambaOne повторит вебхук.
- Счет неизвестен процессингу (404, например ссылка создана не через гейт) или не в KGS — ответ 200:
  повторять бесполезно.
- Вебхуки о возвратах только логируются: статус возврата процессинг опрашивает сам через `refund_status`.
- Id из вебхука экранируется в пути запросов к процессингу, `.`/`..` отклоняются, иначе
  через вебхук можно было бы обратиться к другому ресурсу API процессинга с токеном гейта.

### Возвраты

- Возврат разрешен только для платежа в статусе `COMPLETED` или `REFUNDED` (повторный частичный возврат).
- Процессинг повторяет возврат после таймаута. Если NambaOne отказывает в создании, гейт проверяет,
  не создан ли возврат с этим `refund_id` первой попыткой, и отдает его настоящий статус вместо `failed`.
  Если сумма найденного возврата отличается от запрошенной, в лог пишется ошибка.

### Безопасность

- Секрет терминала (`provider_secret_key`) маскируется в логах входящих запросов и ответов процессинга (`log_masking.py`).
- Невалидные `terminal_data` логируются только путями полей, без значений.
- Без `SECURE_REDIRECT_KEY` подписать редирект мог бы кто угодно, поэтому такая продажа отклоняется
  еще до создания ссылки.

### Производительность

Для терминалов с прокси httpx-клиент создается один раз на каждый `proxy_url` (`ProxyClientPool`),
а не на каждый запрос: создание клиента собирает SSL-контекст и пул соединений.
